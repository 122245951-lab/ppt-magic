# 四层测试方法论：把产品不变量变成自动化断言

> 一套从单测到用户旅程的分层测试方法，帮助"生成式文档产品"守住上文的全部不变量。实测规模：契约 34 断言 / 路由 15 / 旅程 39 / 冒烟 25，共 113 项，全绿后才可发版。

## 一、为什么生成式产品更需要测试

LLM/模板输出是概率性的，但产品承诺是确定性的（版式不破、数字不改、局部编辑不动其它内容）。因此要把**不变量**从口头约束升级为**回归断言**——每次改代码都重跑，防止"某次重构把保真兜底删了"。

## 二、四层结构

### L1 契约单测（引擎层，最快）
直接调用执行器/纯函数，不经过 HTTP。跑一次毫秒级，改引擎必跑。
- 覆盖：大纲分页、局部编辑最小 ops、保真跳过、字号 clamp、图表换型、空选不动。
- 断言风格："只命中目标路径 1 条 op；应用后其余字段 JSON 相等"。
- 示例命令：`npx tsx server/scripts/test-elements.ts`（本地引擎直调）。

### L2 路由端到端（单用户，HTTP）
起真实服务，登录后用 fetch 打 API，验证载荷契约与持久化。
- 覆盖：蓝图/导演稿 PATCH（扁平载荷契约：`typography.headline` 而非 `design.typography.headline`——**前后端载荷形状不一致是全栈最常见的静默 bug**）、路径白名单拒写、备注字段正确路径、错误路径 400。
- 示例命令：`node server/scripts/test-blueprint.mjs`。

### L3 用户旅程（多用户 + SSE）
模拟真实使用顺序：注册 → 登录 → 素材 → 大纲 → 采用 → 点名改元素 → 圈选编辑 → 多步撤销 → 导出 → 越权。
- 必须覆盖跨账号：A 的资源 B 一律 404 且零写入；个人 Provider 对他人不可见；admin 越权改个人配置 404。
- **旅程断言是测出隐藏 bug 的主力**（例如"多步撤销只生效 1 步"只有连续 undo×4 才暴露；"越权返回 500 而非 404"只有跨账号操作才暴露）。
- 示例命令：`node server/scripts/test-journey.mjs`。

### L4 回归冒烟（全量健康检查）
每次发布前快速过一遍主链路健康：登录/生成/保真/撤销/行内编辑/导出/隔离/Key 掩码。
- 示例命令：`npm run test:api`。

## 三、断言设计原则

1. **"其余不变"比"目标变了"更有力**：断言邻居、标题、页脚 JSON 级相等，远强于只断言目标文本不同。
2. **幂等与隔离分开测**：单测覆盖逻辑，旅程覆盖权限。
3. **固定邮箱有冷却**：验证码与 chat 有按邮箱/用户限流，连续跑需换新邮箱或等待，否则误报（cooldown/429 是测试基建问题，不是产品 bug）。
4. **用原文快照对比**：撤销类断言必须与"最初原文"对比，不要与"中途状态"对比（中途文本已被前面步骤改过，会误判）。
5. **含数字素材与无数字素材分开造**：保真用例必须造带数字的句子，局部编辑用例造长句（过短的句子会让"精简"类动作无变化，误报失败）。

## 四、发布门槛

- L1–L4 全绿；
- typecheck（server + web）通过；
- 前端构建产物与后端代码同步发布（静态托管会直接读 dist，改了前端忘 build 是最常见的"改了没生效"）。

## 五、把测试写进文档

把四层命令写进 README"常用脚本"，让"全绿才发版"成为团队习惯而非口头约定。
